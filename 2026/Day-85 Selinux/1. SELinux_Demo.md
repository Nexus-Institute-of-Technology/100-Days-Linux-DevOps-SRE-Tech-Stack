# NIT Academy — SELinux Practical Lab (Rocky Linux 9)

**Course:** Linux System Administration / RHCSA Preparation  
**Level:** Beginner  
**Estimated duration:** 15–20 minutes  
**Lab platform:** Rocky Linux 9 virtual machine  
**Topic:** SELinux subjects, objects, security contexts, enforcing, permissive, and troubleshooting

---

## Learning objectives

By the end of this lab, students will be able to:

1. Identify an SELinux **subject**, **object**, and requested **access**.
2. Explain how **security contexts** and **policy** determine access.
3. Compare **Enforcing** and **Permissive** modes.
4. Inspect SELinux labels and denial events.
5. Repair an incorrect file label without disabling SELinux.

> **Safety:** Perform this lab on a training VM, not a production server. Use a root shell or prefix administrative commands with `sudo`. Do **not** leave the VM in Permissive mode after the exercise.

## 1. Core SELinux terminology

![alt text](<SELinux Key Concepts Infographic.png>)

| Term | Student-friendly meaning | Example in this lab |
|---|---|---|
| **Subject** | A process attempting to use a resource | Apache web server process (`httpd`), normally running in type `httpd_t` |
| **Object** | The resource the subject wants to access | `/var/www/html/selinux-lab.html` |
| **Access** | The operation the subject wants to perform | Read a webpage |
| **Policy** | Rules specifying what subjects may do to objects | Whether `httpd_t` may read a file with a given type |
| **Context** | SELinux security attributes attached to a process or resource | `httpd_t`, `httpd_sys_content_t`, `user_home_t` |
| **Labeling** | Assigning or restoring an SELinux context | `chcon`, `restorecon` |

### Our lab in one picture
![alt text](<SELinux Made Simple_ Secure Access Explained.png>)

```text
       SUBJECT                REQUESTED ACCESS                 OBJECT
   Apache (httpd_t)  ---------------- READ ----------------> Webpage
          |                                                   |
          |                                            File security label
          |                                          (e.g., user_home_t)
          |                                                   |
          +---------------------- SELinux POLICY -------------+
                                     |
                              ALLOW or DENY?
```

**Teaching analogy:** A subject is an employee, an object is a restricted room, access is entering the room, context is their security designation, and policy determines whether entry is allowed.

## 2. What we will demonstrate

We will create a normal Apache webpage, deliberately assign it an incorrect SELinux type, and compare the result in two modes.

| SELinux mode / situation | What SELinux does | Expected web request |
|---|---|---|
| **Enforcing**, correct file label | Allows Apache to read authorized web content | `200 OK` |
| **Enforcing**, incorrect file label | Blocks a policy-violating read | Typically `403 Forbidden` |
| **Permissive**, incorrect file label | Logs a would-be denial but does not block it | `200 OK` |
| **Enforcing**, label restored | Allows the read again | `200 OK` |

**Important:** Apache still depends on normal Linux discretionary access controls (DAC), service configuration, and file availability. SELinux is an additional layer of security; Permissive mode does not override ordinary file permissions.

## 3. Prepare the Rocky Linux VM

### Step 3.1 — Become root

```bash
sudo -i
```

### Step 3.2 — Check SELinux status

```bash
getenforce
sestatus
```

Expected mode:

```text
Enforcing
```

If it says **Permissive**, temporarily change to Enforcing:

```bash
setenforce 1
getenforce
```

If it says **Disabled**, `setenforce` cannot activate SELinux. The VM must first be configured to boot with SELinux enabled, and then restarted. Ask the instructor before changing the VM's boot configuration.

### Step 3.3 — Install and start Apache

```bash
dnf install -y httpd curl audit
systemctl enable --now httpd
systemctl status httpd --no-pager
```

Expected: `active (running)`.

> The lab uses `http://localhost` from within the VM, so opening a firewall port to external clients is unnecessary.

## 4. Create a test webpage

Create a separate test file to avoid changing an existing website:

```bash
echo "Welcome to NIT Academy SELinux Lab" > /var/www/html/selinux-lab.html
chmod 644 /var/www/html/selinux-lab.html
restorecon -v /var/www/html/selinux-lab.html
```

Inspect its security context:

```bash
ls -Z /var/www/html/selinux-lab.html
```

Look for the type:

```text
httpd_sys_content_t
```

Test the webpage:

```bash
curl -i http://localhost/selinux-lab.html
```

Expected HTTP status:

```text
HTTP/1.1 200 OK
```

And the response body should include:

```text
Welcome to NIT Academy SELinux Lab
```

**Ask the class:** What is the *subject*? What is the *object*? What is the *requested access*?

## 5. Deliberately create an SELinux label problem

Change **only the test file's** SELinux type to a user-home-file type:

```bash
chcon -t user_home_t /var/www/html/selinux-lab.html
```

Verify the label:

```bash
ls -Z /var/www/html/selinux-lab.html
```

Look for:

```text
user_home_t
```

Try accessing the webpage:

```bash
curl -i http://localhost/selinux-lab.html
```

**Expected on a default, SELinux-confined Apache installation:**

```text
HTTP/1.1 403 Forbidden
```

**Why?** Apache's process domain (`httpd_t`) ordinarily cannot read this file type under the default policy, even though the file still has ordinary `644` permissions.

### Optional checks

```bash
ls -l /var/www/html/selinux-lab.html
ps -eZ | grep '[h]ttpd'
getenforce
```

The `ls -l` command shows traditional Linux permissions. The `ls -Z` command shows SELinux labeling. These are **different controls**.

> If you do not get a `403 Forbidden`, confirm that SELinux is Enforcing, `httpd` is confined, the `curl` request hits the correct local VM, and that the file label really changed to `user_home_t`. Your VM's policy or configuration may differ from the default.

## 6. Change to Permissive mode

Temporarily switch modes:

```bash
setenforce 0
getenforce
```

Expected:

```text
Permissive
```

Repeat the request:

```bash
curl -i http://localhost/selinux-lab.html
```

Expected:

```text
HTTP/1.1 200 OK
```

The response should again contain:

```text
Welcome to NIT Academy SELinux Lab
```

**Explanation:** In Permissive mode, SELinux evaluates policy and generally records would-be denials, but does **not** block the operation because of SELinux policy. Ordinary Linux permissions and application settings are still active.

**Discussion:** Why does the same file work in Permissive mode when it failed in Enforcing mode?

## 7. Review the SELinux denial

Generate a recent request while the file still has the wrong label, and search the audit records:

```bash
curl -s -o /dev/null http://localhost/selinux-lab.html
ausearch -m AVC,USER_AVC -ts recent
```

Look for lines similar to these **illustrative excerpts** (actual details vary):

```text
avc:  denied  { read }  for  comm="httpd" ...
scontext=system_u:system_r:httpd_t:s0
tcontext=system_u:object_r:user_home_t:s0
tclass=file
```

| Audit field | Meaning |
|---|---|
| `comm="httpd"` | Process responsible for the request |
| `scontext=...httpd_t...` | SELinux security context of the subject |
| `tcontext=...user_home_t...` | SELinux security context of the object |
| `denied { read }` | A read was not permitted by SELinux policy |
| `tclass=file` | The target object's class is a file |

Other useful commands:

```bash
systemctl status auditd --no-pager
journalctl -k --no-pager | grep -i 'avc:.*denied' | tail -10
```

If the audit daemon is running, the records are generally stored in `/var/log/audit/audit.log`. Logging may differ depending on audit configuration, and repeated denials may be suppressed by policy or logging settings.

**Important correction to a common simplified explanation:** SELinux does not automatically log every system call just because it is Enforcing or Permissive. It typically logs **policy denials or would-be denials** when audit logging is configured. A successful, permitted request usually does not produce an AVC denial.

## 8. Restore Enforcing and repair the label

### Step 8.1 — Switch SELinux back to Enforcing

```bash
setenforce 1
getenforce
```

Expected:

```text
Enforcing
```

The file still has the wrong label. Confirm the request is blocked again:

```bash
curl -i http://localhost/selinux-lab.html
```

Expected: `403 Forbidden`.

### Step 8.2 — Restore the correct SELinux label

```bash
restorecon -v /var/www/html/selinux-lab.html
ls -Z /var/www/html/selinux-lab.html
```

Look for:

```text
httpd_sys_content_t
```

### Step 8.3 — Test one final time

```bash
curl -i http://localhost/selinux-lab.html
```

Expected:

```text
HTTP/1.1 200 OK
```

**Result:** Students have repaired an SELinux access problem **without disabling SELinux**.

## 9. How this relates to system calls

A simplified conceptual sequence for a web request is:

```text
Browser/curl requests a webpage
            |
            v
Apache process (SUBJECT) tries to open/read file (OBJECT)
            |
            v
Normal Linux permissions + SELinux security checks
            |
            +---- SELinux Disabled: no SELinux policy enforcement
            |
            +---- SELinux Permissive: would-be SELinux denial logged;
            |                         SELinux does not block
            |
            +---- SELinux Enforcing: SELinux policy allows or denies
                                        |
                                 +------+------+
                                 |             |
                               ALLOW         DENY
                                 |             |
                            File read     Access error;
                            succeeds*     Apache may return 403

* Provided normal permissions and other system checks also allow it.
```

An Apache file read involves ordinary Linux system calls, but it is more accurate to say that SELinux checks the **requested access** through Linux security hooks rather than claiming it generates one FTP or HTTP system call and terminates the entire call or service whenever a request is denied.

## Quick command cheat sheet

| Command | Purpose |
|---|---|
| `getenforce` | Check current SELinux mode |
| `sestatus` | Show more detailed SELinux status |
| `setenforce 0` | Temporarily set Permissive mode |
| `setenforce 1` | Temporarily set Enforcing mode |
| `ls -Z /path/to/file` | View a file's SELinux context |
| `ps -eZ` | View process SELinux contexts |
| `chcon -t user_home_t FILE` | Temporarily relabel a file for this lab |
| `restorecon -v FILE` | Restore a file's expected SELinux label |
| `ausearch -m AVC,USER_AVC -ts recent` | View recent audit denial records |
| `curl -i URL` | Show the HTTP response headers and body |

> **Remember:** `chcon` changes a label directly; a later `restorecon` or full filesystem relabel can replace it with the policy-defined default. For persistent custom file-label mappings, administrators typically use `semanage fcontext` followed by `restorecon`.

### Final takeaway

> **Subject + Object + Requested Access + Security Contexts + SELinux Policy = Allow or Deny.**
>
> **The correct administrator response is to troubleshoot and repair SELinux problems — not automatically disable SELinux.**
