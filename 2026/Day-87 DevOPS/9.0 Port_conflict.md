## 1. Why port allocation matters

Multiple web applications often choose the same default **TCP port 8080**. On a single host IP address, independent processes generally **cannot bind the same TCP listening port at the same time**. A port conflict produces errors such as `java.net.BindException: Address already in use` or `bind() ... failed`.

A **service process running** does not guarantee that its intended HTTP port is listening. In this lab, Tomcat's Java process was running and its shutdown listener on **8005** was present, but the HTTP Connector on **8080** failed because 8080 was in use when Tomcat started. Tomcat needed to be restarted after freeing the port.

**Important distinctions:**

- A listener is identified by **protocol + local IP address + port**, not port alone.
- `127.0.0.1:8080` is restricted to local clients; `0.0.0.0:8080` listens on all IPv4 interfaces, potentially conflicting with specific-IP listeners.
- TCP 8080 and UDP 8080 are different transport endpoints.
- Containers have their own network namespaces; a Tomcat container can listen on `8080` internally while the host publishes it as `8083`.
- `ss` identifies listening sockets; `ps`, `/proc/<PID>/cmdline`, service units, and logs identify the application and reason for failure.

## 2. Recommended lab port allocation plan

**NIT Academy recommendation for ONE Rocky Linux VM (planned, not confirmed as currently active):**

| Application | Common default | Proposed host port | Protocol | Exposure | Configuration / control |
|---|---:|---:|---|---|---|
| SSH | 22 | **22** | TCP | Admin / trusted network only | `/etc/ssh/sshd_config` |
| Apache HTTPD | 80 | **80** | TCP | LAN web lab | `/etc/httpd/conf/httpd.conf`, virtual hosts |
| Apache Tomcat | 8080 | **8080** | TCP | LAN web lab | `/opt/tomcat/conf/server.xml` |
| Jenkins | 8080 | **8081** | TCP | Trusted LAN / VPN only | `systemctl edit jenkins` |
| NGINX | 80 | **8082** | TCP | LAN web lab | Active NGINX `server` block |
| Dockerized Tomcat | 8080 in container | **8083 → 8080** | TCP | Host loopback by default | Docker `-p` / Compose `ports` |
| HTTPS front end (future) | 443 | **443** | TCP | Approved entry point | NGINX TLS reverse proxy |

**Allocation rules:**

1. Confirm the candidate port is unused on the intended IP/protocol **before assigning it**.
2. Record both internal and externally published ports for containers.
3. Reserve **80/443** for a web entry point in a production-style design; backend applications may use loopback listeners.
4. Do not expose Jenkins admin functions to the public internet without a properly secured access design.
5. A registered port is not necessarily safe or free; review SELinux, firewall, app dependencies, monitoring, and reverse-proxy rules.
6. Each change must have an owner, reason, approval, validation record, and rollback plan.

### Proposed lab topology

```text
Training clients
      |
Rocky Linux VM (example IP: 192.168.1.98 — verify yours)
      |-- TCP 22    SSH
      |-- TCP 80    Apache HTTPD
      |-- TCP 8080  Tomcat
      |-- TCP 8081  Jenkins
      |-- TCP 8082  NGINX
      `-- TCP 8083  Docker host -> Tomcat container TCP 8080
```

> **Production alternative:** Put NGINX on **80/443**, move or stop HTTPD on those ports, terminate TLS on the reverse proxy, and route `app.example.com` to Tomcat, `ci.example.com` to Jenkins, etc. Use real DNS names and certificates, and secure backend access.

## 3. Industry architecture and security policy

**Single VM, training:** Unique host ports are simplest because students can observe each application separately.

**Typical production:** A reverse proxy, ingress controller, or load balancer receives HTTP/HTTPS, commonly on TCP **80/443**, and routes requests by hostname or path to distinct backend ports. A production deployment may place services in different VMs, hosts, or container networks instead of one VM.

```text
Browser -- HTTPS 443 --> NGINX reverse proxy
                           |-- app.example.com --> 127.0.0.1:8080 (Tomcat)
                           |-- ci.example.com  --> 127.0.0.1:8081 (Jenkins)
                           `-- lab.example.com --> 127.0.0.1:8083 (Docker host mapping)
```

**Exposure policy:** Start with `127.0.0.1` for backends that are only accessed through the reverse proxy. Open firewalld and upstream ACL rules only where needed. Monitor services and document DNS/TLS ownership as well as port ownership. Configure Jenkins' external URL appropriately when placing it behind a reverse proxy.

## 4. Discover actual listeners before changing anything

Run as root, or use `sudo` where appropriate:

```bash
hostnamectl --static
ip -br addr
ss -tulpn
ss -lntp
ss -lntp '( sport = :8080 )'
ps -ef | grep '[o]rg.apache.catalina.startup.Bootstrap'
systemctl status httpd nginx jenkins --no-pager
systemctl cat jenkins
nginx -T 2>&1 | grep -n 'listen'
```

If a specific PID owns a port:

```bash
ps -fp <PID>
tr '\0' ' ' < /proc/<PID>/cmdline; echo
readlink -f /proc/<PID>/exe
```

Replace `<PID>` with the **actual process ID**, for example `35999`. The executable path alone may identify Java without identifying which Java application is running; look for `org.apache.catalina.startup.Bootstrap`, `jenkins.war`, and configured paths.

## 5. Standard change procedure

- [ ] **Request:** State why the port needs to change; list affected services, DNS, agents, and users.
- [ ] **Inventory:** Capture hostname, IP/interface, protocol, current port, owner/PID, and exposure.
- [ ] **Pre-check:** Confirm candidate port is available; inspect conflicting IPv4/IPv6 bindings.
- [ ] **Approval:** Obtain authorization before changing a shared machine.
- [ ] **Backup:** Save the actual config/unit and its current effective settings.
- [ ] **Change:** Modify the application listener or Docker publishing rule.
- [ ] **Security:** Review SELinux domain/type, firewall zone, upstream ACL, and access policy.
- [ ] **Validate syntax:** Run app-specific syntax tests where available.
- [ ] **Restart/reload:** Use the app's supported method; confirm there is no startup error.
- [ ] **Verify:** Check `ss`, process identity, HTTP response, logs, and client connectivity.
- [ ] **Document:** Enter date/time, approver, commands, evidence, final status, and rollback.

**Do not edit `/etc` files blindly.** Confirm how the program was installed and which configuration it really uses.

## 6. Jenkins: change 8080 to 8081

**Applies to a Jenkins RPM/systemd installation that uses `JENKINS_PORT`.** Other installations may differ.

Inspect:

```bash
systemctl cat jenkins
systemctl is-active jenkins
ss -lntp '( sport = :8081 )'
```

Create or edit the systemd drop-in:

```bash
systemctl edit jenkins
```

Add between the editor's designated override markers:

```ini
[Service]
Environment="JENKINS_PORT=8081"
```

Apply and verify:

```bash
systemctl daemon-reload
systemctl restart jenkins
systemctl show jenkins -p Environment
systemctl status jenkins --no-pager
ss -lntp '( sport = :8081 )'
curl -I http://127.0.0.1:8081/
```

**Also review:** Jenkins URL, agent configuration, reverse proxy, firewall, and monitoring checks. An HTTP redirect or login response may be normal; evaluate the actual result.

**Rollback:** Restore the prior drop-in settings (remove only the change you added), run `systemctl daemon-reload`, restart Jenkins, and verify the previous listener. Do not blindly `revert` a shared unit if other customizations exist.

## 7. Tomcat: HTTP connector port

Your running instance was confirmed with `-Dcatalina.home=/opt/tomcat`. Verify this location still applies before editing.

```bash
ls -ld /opt/tomcat
cp -a /opt/tomcat/conf/server.xml \
  /opt/tomcat/conf/server.xml.bak-$(date +%F-%H%M%S)
grep -n -A 6 '<Connector port=' /opt/tomcat/conf/server.xml
vi /opt/tomcat/conf/server.xml
```

Example active HTTP Connector:

```xml
<Connector port="8080" protocol="HTTP/1.1"
           connectionTimeout="20000"
           redirectPort="8443" />
```

**Final plan:** Tomcat stays on **8080**. To practice changing it, temporarily edit only `port="8080"` to `port="8090"`, then restore it. **Port 8005 is traditionally Tomcat's shutdown port**, not the web port.

For a Tomcat instance started by the Tomcat scripts:

```bash
/opt/tomcat/bin/shutdown.sh
/opt/tomcat/bin/startup.sh
ss -lntp '( sport = :8090 )'   # if practicing 8090
curl -I http://127.0.0.1:8090/
tail -50 /opt/tomcat/logs/catalina.out
```

If managed by systemd, use its `systemctl restart tomcat` service instead. Check that the old process actually exited before restarting.

**Rollback:** Restore the saved `server.xml` (or edit the Connector back to 8080), restart, verify the correct port, and document results.

**Troubleshooting from this lab:** `java.net.BindException: Address already in use` indicates a bind conflict. After stopping the program that had the port, restart Tomcat because a failed Connector does not necessarily retry automatically.

## 8. NGINX: change its lab listener to 8082

Discover active server blocks first:

```bash
nginx -T 2>&1 | grep -n 'listen'
grep -Rni 'listen ' /etc/nginx/nginx.conf /etc/nginx/conf.d/
```

**Back up the exact file you edit**, then change the relevant active listener. Example:

```nginx
server {
    listen 8082;
    server_name _;

    location / {
        root /usr/share/nginx/html;
        index index.html;
    }
}
```

Check for duplicate `server` definitions and separately configured IPv6 `listen [::]:...` directives.

```bash
nginx -t
systemctl restart nginx
ss -lntp '( sport = :8082 )'
curl -I http://127.0.0.1:8082/
```

**Rollback:** Restore the saved configuration, `nginx -t`, restart/reload, verify the old listener and record the result.

> When moving to the production-style reverse proxy lab, assign NGINX **80/443** instead. Stop or move HTTPD off port 80 first, and configure appropriate TLS and proxy routes.

## 9. Apache HTTPD: keep port 80

Check all `Listen` directives:

```bash
grep -RniE '^[[:space:]]*Listen ' /etc/httpd/conf /etc/httpd/conf.d
cp -a /etc/httpd/conf/httpd.conf \
  /etc/httpd/conf/httpd.conf.bak-$(date +%F-%H%M%S)
```

For the recommended lab plan, use:

```apache
Listen 80
```

For a controlled practice exercise, change **the active** `Listen 80` to `Listen 8084`, checking virtual host definitions and additional Listen directives as needed.

```bash
httpd -t
systemctl restart httpd
ss -lntp '( sport = :8084 )'  # if practicing 8084
curl -I http://127.0.0.1:8084/
```

**Rollback:** Restore `Listen 80`, validate, restart, verify TCP 80 and client access. `semanage port` does **not** change HTTPD's `Listen` directive.

## 10. Docker: publish host 8083 to container 8080

A mapping of `127.0.0.1:8083:8080` means **host IP 127.0.0.1 / host port 8083 → container port 8080**. The containerized Tomcat itself can continue listening on 8080.

### Docker CLI

```bash
docker run -d --name tomcat-lab \
  -p 127.0.0.1:8083:8080 \
  tomcat:9.0

docker ps
docker port tomcat-lab
docker logs --tail 50 tomcat-lab
curl -I http://127.0.0.1:8083/
```

A fresh Tomcat image may return HTTP **404** without a deployed ROOT webapp; this is different from a TCP connection failure.

### Docker Compose (`compose.yaml`)

```yaml
services:
  tomcat:
    image: tomcat:9.0
    ports:
      - "127.0.0.1:8083:8080"
```

```bash
docker compose up -d
docker compose ps
docker compose logs --tail=50 tomcat
```

To change a published host port, edit the Compose mapping and **recreate the container** using `docker compose up -d`; an existing standalone container also generally needs to be recreated. Do not confuse container *internal* ports with host-published ports.

**Access policy:** The example above is accessible only from the Docker host. To reach it from other student machines, use a reviewed LAN-IP binding or route through a reverse proxy; do not expose an admin interface through all host interfaces without approval.

**Rollback:** Restore the original `ports` mapping and recreate; verify `docker ps`, access, and logs. Preserve named volumes and persistent data when recreating containers.

## 11. SELinux, firewall, and access controls

Three different layers can prevent access:

| Layer | Diagnostic | Typical adjustment |
|---|---|---|
| Application | `ss -lntp`; app logs | Change `Listen`, `listen`, Connector, Jenkins setting, or Docker mapping |
| SELinux | `getenforce`; `semanage port -l` | Authorize a bind port for the **correct process domain/type** |
| Firewall/network | `firewall-cmd --list-all`; upstream ACL | Allow remote traffic only where required |

Inspect:

```bash
getenforce
semanage port -l | grep http_port_t
firewall-cmd --get-active-zones
firewall-cmd --list-all
```

**Illustrative SELinux command only:** If port 8082 is unassigned, the web service is governed by a domain permitted to bind `http_port_t`, and the policy requires it:

```bash
semanage port -a -t http_port_t -p tcp 8082
```

If a port already has a type, investigate its current labeling and policy before using `-m`; do not blindly relabel a shared port. Jenkins may run under a different SELinux domain. Never disable SELinux simply to bypass a bind denial.

**Illustrative firewall opening only if LAN access is approved:**

```bash
firewall-cmd --permanent --add-port=8082/tcp
firewall-cmd --reload
firewall-cmd --list-ports
```

Opening the firewall does not start the application. Likewise, binding the service locally does not imply that remote traffic is allowed.

## 12. Troubleshooting and verification

| Symptom | Likely causes | Checks |
|---|---|---|
| `Address already in use` | Port collision, wildcard or IPv6 binding | `ss -lntp`, inspect process PID, logs |
| Process running but no 8080 listener | HTTP Connector failed; different configured port | Application logs, `server.xml`, `ss` |
| `Connection refused` | No active listener on selected IP:port | `ss -lntp`, `curl -v`, restart status |
| Local curl works, remote browser fails | Firewall, bind to localhost, routing/ACL | `ss`, `firewall-cmd`, host IP, network policy |
| Bind denied under SELinux | Port label / service domain mismatch | `getenforce`, SELinux audit logs, `semanage port -l` |
| HTTP 404 from container | No app deployed at request path | `docker ps`, logs, test correct URL |
| Jenkins still uses old port | Override not effective, different install mode | `systemctl cat`, `systemctl show ... -p Environment`, logs |

### Evidence collection sample

```bash
hostnamectl --static
ip -br addr
ss -lntp
systemctl status httpd nginx jenkins --no-pager
ps -ef | grep '[o]rg.apache.catalina.startup.Bootstrap'
docker ps --format 'table {{.Names}}\t{{.Ports}}'
getenforce
firewall-cmd --list-all
```

Use `curl -I http://127.0.0.1:PORT/` for HTTP checks. Not every valid application returns `200`; `301`, `302`, `401`, or even `404` may show that the HTTP server is reachable, but require further application validation.
