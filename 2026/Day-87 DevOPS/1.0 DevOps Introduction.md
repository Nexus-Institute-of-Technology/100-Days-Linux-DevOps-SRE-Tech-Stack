# 1.0 DevOps Introduction — Building a Complete CI/CD Pipeline

**NIT Academy | DevOps Project Series | Lesson 1**

## 🎯 Learning Objectives

By the end of this lesson, students should be able to:

1. Explain how Git, GitHub, Jenkins, Maven, Ansible, Docker, Kubernetes, and AWS work together.
2. Describe the logical flow of a DevOps project from source code to deployment.
3. Identify the role of each tool in a CI/CD pipeline.
4. Distinguish deployment to a virtual machine, a Docker container, and Kubernetes.
5. Outline the stages of a hands-on Java application delivery project.

## 1. Introduction

Knowing individual DevOps tools is useful, but understanding **how they collaborate** is what makes it possible to deliver software consistently.

This course follows a practical project: **build and deploy a Java application using a complete CI/CD workflow**. The goal is to connect the tools into one logical process rather than study them as isolated technologies.

## 2. Tools Used in the Project

| Tool | Role in this project | What it does |
|---|---|---|
| **Git** | Local version control | Tracks source-code changes on the developer's computer |
| **GitHub** | Remote/distributed code hosting | Stores the shared Git repository and enables collaboration |
| **Jenkins** | Continuous integration (CI) | Orchestrates the build pipeline after code changes |
| **Maven** | Java build tool | Compiles, tests, and packages the Java application into an artifact |
| **Ansible** | Configuration management and deployment | Automates deployment to target environments |
| **Docker** | Containerization | Packages and runs the application in a container |
| **Kubernetes** | Container orchestration | Deploys and manages containerized applications |
| **AWS** | Infrastructure platform | Hosts the machines and environments used for the project |

> **Terminology note:** Git is a *distributed version control system* even when used locally. GitHub is a remote hosting and collaboration service for Git repositories. The lecture's distinction between “local Git” and “distributed GitHub” is a useful workflow shorthand, not a strict classification.

## 4. Step-by-Step DevOps Workflow

### Step 1 — Developers Write the Application

A developer creates or updates Java application code on a workstation. The project files are tracked with **Git**.

```bash
git status
git add .
git commit -m "Update Java application"
```

### Step 2 — Push Code to GitHub

The developer shares committed changes with the team by pushing to a GitHub repository.

```bash
git push origin main
```

**Result:** The latest source code is available in the remote repository.

### Step 3 — Jenkins Starts the CI Pipeline

**Jenkins** retrieves the code and runs the configured build process. A webhook or other configured trigger can start the pipeline after a push.

**Result:** Builds become repeatable rather than requiring someone to run each step manually.

### Step 4 — Maven Builds the Java Application

Jenkins invokes **Maven** to compile, test, and package the code.

```bash
mvn clean package
```

Depending on the project configuration, Maven may generate a **`.jar`** or **`.war`** artifact.

**Result:** A deployable application artifact is ready.

### Step 5 — Ansible Deploys the Application

**Ansible** automates the deployment process, helping avoid manual differences between servers. In this project, Ansible is used to deploy the application to the selected target.

**Result:** The same deployment process can be repeated consistently.

### Step 6 — Deploy to a Virtual Machine

The **first deployment target** is a VM hosted in the AWS environment.

```text
AWS Infrastructure
      |
      v
Virtual Machine
      |
      v
Java Runtime / Application Server
      |
      v
Deployed Java Application
```

This stage teaches students how application artifacts are deployed to a conventional server.

### Step 7 — Deploy Using Docker

The **second deployment target** is a Docker container. The application and its required runtime components are packaged in a container image and run as a container.

```text
AWS Host / VM
      |
      v
Container Runtime
      |
      v
Docker Container
      |
      v
Java Application
```

**Result:** The application can be packaged and deployed more consistently across compatible environments.

### Step 8 — Deploy Using Kubernetes

The **final deployment target** is Kubernetes, which manages containerized applications.

```text
AWS Infrastructure
      |
      v
Kubernetes Cluster
      |
      v
Deployment
      |
      v
Pods (Application Containers)
```

**Result:** Students learn the basic transition from running a single container to managing containerized workloads through orchestration.

## 5. Understanding CI and CD

| Term | Meaning | In this project |
|---|---|---|
| **CI** | Continuous Integration | Jenkins builds and tests changes using Maven |
| **CD** | Continuous Delivery or Continuous Deployment | The application is prepared for release or automatically deployed, depending on pipeline configuration |

**Important:** A pipeline is not automatically “continuous deployment” just because Jenkins is installed. Deployment automation and release approvals must be configured. This introductory lecture outlines the planned workflow; it does not yet provide the Jenkinsfile or deployment scripts.

## 6. Three Deployment Stages Compared

| Stage | Target | Main lesson |
|---|---|---|
| **Stage 1** | Virtual Machine | Deploy a Java artifact to a conventional server |
| **Stage 2** | Docker | Package and run the application in a container |
| **Stage 3** | Kubernetes | Manage application containers with orchestration |

These are **successive learning stages**, not three mandatory destinations for every production deployment.

## 7. Hands-On Project Roadmap

Students will eventually complete the following workflow:

## 9. Common Beginner Mistakes

| Mistake | Correction |
|---|---|
| Thinking Git and GitHub are the same thing | Git is version control; GitHub hosts and shares Git repositories |
| Thinking Jenkins compiles Java by itself | Jenkins orchestrates tools such as Maven |
| Confusing an artifact with a container image | A JAR/WAR is an application artifact; a container image packages an application and its runtime requirements |
| Thinking Docker and Kubernetes have identical roles | Docker is associated with building/running containers; Kubernetes orchestrates containerized workloads |
| Assuming AWS is a CI/CD tool | AWS provides infrastructure and services where the pipeline and applications can run |
| Assuming every pipeline deploys automatically | Deployment behavior depends on how the pipeline is configured |

## 📖 Key Takeaways

- DevOps tools become most useful when connected into a complete workflow.
- **Git and GitHub** manage and share source code.
- **Jenkins and Maven** automate the build process and produce artifacts.
- **Ansible** automates deployment.
- **Docker** introduces container-based packaging and execution.
- **Kubernetes** introduces container orchestration.
- **AWS** provides the infrastructure for this course project.
- The course progressively deploys one Java application to a **VM**, then **Docker**, and finally **Kubernetes**.

## ⭐ Golden Rule

> **Learn the flow, not just the tools: Code → Commit → Build → Package → Deploy → Run.**
