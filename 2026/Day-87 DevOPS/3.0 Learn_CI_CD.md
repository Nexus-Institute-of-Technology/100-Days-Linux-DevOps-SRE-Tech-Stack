## 1. Introduction

In this lecture, we will examine three important DevOps practices:

- **Continuous Integration (CI)**
- **Continuous Delivery**
- **Continuous Deployment**

They describe how teams integrate source code, build and test applications, and release those applications to target environments.

The lecture uses an AWS CI/CD workflow diagram as its conceptual reference and then applies the same ideas to our course project.

## 2. Continuous Integration (CI)

Developers usually begin with source code on their **local workstations**. They commit their changes to a **version control system**, also called a **source code management (SCM) system**.

In this course:

- **Git** manages source-code versions.
- **GitHub** hosts the shared remote repository.
- **Jenkins** automates the integration pipeline.
- **Maven** compiles and builds the Java application.

When new code becomes available in GitHub, Jenkins can automatically retrieve the code, build it with Maven, and run unit tests.

### CI workflow

```text
Developer's Workstation
         |
         | git commit / git push
         v
     GitHub Repository
         |
         | webhook or polling
         v
        Jenkins
         |
         +--> Retrieve source code
         +--> Maven compile/build
         +--> Run unit tests
         |
         v
    Build Artifact (e.g., .war or .jar)
```

**Definition:** Continuous Integration is the practice of frequently integrating code changes into a shared repository and automatically validating them through builds and tests.

> **Important:** A successful CI build produces a validated artifact, but does **not** necessarily mean the application has been deployed.

## 3. What Is a Build Artifact?

An **artifact** is the output generated by the build process.

For a Java project using Maven, examples include:

| Artifact | Typical use |
|---|---|
| `.jar` | Packaged Java application or library |
| `.war` | Java web application deployed to a compatible application server, such as Tomcat |

Example Maven command:

```bash
mvn clean package
```

This command cleans previous build outputs and packages the project according to its `pom.xml` configuration. Tests normally run during the Maven build unless explicitly skipped.

## 4. Deployment Environments

After the build artifact is generated, it must be deployed to a target environment.

The lecture mentions environments such as:

| Environment | Purpose |
|---|---|
| Development (Dev) | Developers build and check changes |
| Testing / QA | Testers validate application behavior |
| Staging | Pre-release environment for realistic testing |
| Pre-production | Final verification before production, where used |
| Production | Live application used by customers |

Not every organization uses all of these environments. Their names and release procedures vary by project.

### Typical release path

```text
Build Artifact
     |
     v
Staging Environment
     |
     +--> Regression Tests
     +--> Performance Tests
     |
     v
Production Environment
```

**Regression testing** checks that recent changes have not broken existing behavior. **Performance testing** evaluates how the application performs under expected workloads.

## 5. Continuous Delivery

**Continuous Delivery** keeps software in a deployable state through automated builds, tests, and release preparation. A production release can be performed on demand.

In the lecture's example, **manual approval is required before deploying to production**.

```text
GitHub --> Jenkins --> Maven --> Tests --> Staging
                                         |
                                         v
                                  Manual Approval
                                         |
                                         v
                                     Production
```

The pipeline automates the technical work, but a person authorizes the final production release.

**Example:** A release manager reviews the staging test results and approves deployment to production.

## 6. Continuous Deployment

**Continuous Deployment** extends the automated pipeline so that changes passing the required quality gates are **released to production automatically**, without a manual production approval step.

```text
GitHub --> Jenkins --> Maven --> Automated Tests
                                         |
                                         v
                                   Staging Checks
                                         |
                                         v
                              Automatic Production
                                   Deployment
```

The lecture emphasizes that both staging and production deployment can be automated. The distinguishing feature is that **production deployment does not wait for a manual approval**.

> **Clarification:** Continuous Delivery does not require a manual approval at every stage. The key distinction is that Continuous Deployment automatically releases qualifying changes to production, while Continuous Delivery leaves the production release as a separate decision.

## 7. CI vs. Continuous Delivery vs. Continuous Deployment

| Practice | Primary purpose | Typical automation | Production release |
|---|---|---|---|
| **Continuous Integration** | Integrate and validate code | Retrieve code, compile, build, unit test | Not required |
| **Continuous Delivery** | Keep software ready for release | CI plus packaging, deployment preparation, and validation | Released on demand; may require approval |
| **Continuous Deployment** | Automatically release validated changes | CI plus automated testing and release pipeline | Automatic after required checks pass |

**Memory aid:**

- **CI:** *Can we build and test the change?*
- **Continuous Delivery:** *Is the change ready to release?*
- **Continuous Deployment:** *Can a passing change go live automatically?*

## 8. Applying CI/CD to Our DevOps Project

Our course project uses these tools:

| Tool | Role in our project |
|---|---|
| **Git** | Local version control |
| **GitHub** | Shared source-code repository |
| **Jenkins** | CI/CD pipeline orchestration |
| **Maven** | Compile, test, and package the Java application |
| **Ansible** | Automate configuration and deployment tasks |
| **Docker** | Package and run the application in containers |
| **Kubernetes** | Manage and deploy containers on a cluster |

### Project workflow

```text
        Developer Workstation
                 |
             Git / Push
                 |
                 v
               GitHub
                 |
                 v
               Jenkins
                 |
                 v
          Maven Build + Tests
                 |
                 v
           Java Artifact
                 |
                 v
        Ansible Automation
                 |
                 +--> Build / tag container image
                 |
                 +--> Push image to registry
                 |
                 +--> Deploy to Kubernetes
                 |
                 v
          Kubernetes Cluster
                 |
                 v
         Running Application
```

**Technical note:** Maven produces the Java artifact; Docker or another OCI-compatible image builder creates the container image. Ansible can **orchestrate** those commands and deployments. The image is typically pushed to a container registry such as Docker Hub, not committed as a binary into GitHub.

### How the lecture maps to the pipeline

**Continuous Integration portion:**

1. Developer pushes code to GitHub.
2. Jenkins detects or retrieves the change.
3. Maven builds the Java application.
4. Automated tests run.
5. A build artifact is produced.

**Deployment portion:**

1. Ansible orchestrates container image creation.
2. The image is published to a registry.
3. Ansible or the pipeline applies Kubernetes deployment instructions.
4. Kubernetes runs the updated application.

Whether this is **Continuous Delivery** or **Continuous Deployment** depends on the release policy, particularly whether production deployment requires manual approval.

## 10. Common Student Mistakes

1. **Confusing Git with GitHub:** Git is a version-control system; GitHub hosts repositories.
2. **Thinking CI means production deployment:** CI focuses on integrating, building, and testing code.
3. **Treating a build artifact as a container image:** A WAR/JAR and an OCI container image are different deliverables.
4. **Assuming every automated deployment is Continuous Deployment:** The distinction concerns automatic release to production.
5. **Saying Ansible compiles Java by itself:** Maven builds Java; Ansible can trigger or coordinate the process.
6. **Ignoring tests and approvals:** Automated delivery still needs quality and security checks.

## 📖 Key Takeaways

- CI begins when developers integrate code into a shared repository and automated checks validate it.
- Maven can compile Java source code and generate deployable artifacts.
- Delivery pipelines can promote artifacts through staging and production environments.
- Continuous Delivery supports controlled, on-demand production releases.
- Continuous Deployment automatically releases changes to production after they pass required checks.
- Our course connects **GitHub → Jenkins → Maven → Ansible → Docker → Kubernetes** into one end-to-end DevOps workflow.

## ⭐ Golden Rule

> **CI builds confidence in the code. Continuous Delivery makes releases ready. Continuous Deployment releases passing changes automatically.**
