The STEPS below will help you Create Username, User email, Initialize Repository, Check Status, STAGE, ADD, COMMIT & PUSH code to GitHub from your local PC:

### What is an Artifact => “WAR/JAR/EAR/zip” FILES

In build/CI tools (Maven, Gradle, Jenkins, etc.), an artifact is the packaged output of your build an immutable file you can deploy or distribute. Examples: .war, .jar, .ear, Docker images, .zip, etc.  
In Jenkins, you might “Archive the artifacts” so the build’s outputs are saved.  
In Maven, artifacts are published to a repository (e.g., Nexus/Artifactory) and identified by coordinates: groupId:artifactId:version[:packaging][:classifier].  
What “immutable artifact” really means?  
Build once, run many times. The exact bits that passed tests are the ones you deploy.  
Never overwrite a release. 1.2.3 stays 1.2.3 forever; fixes go to 1.2.4.  
Enforced by tooling, not filesystem flags:  
Maven/Gradle: release versions (no -SNAPSHOT) + repository rules that disable redeploy/overwrite of releases (e.g., Nexus/Artifactory).  
Checksums & signatures (SHA-256, GPG) to detect tampering.  
Content-addressable IDs (e.g., container image digests @sha256:...) and pinning to digests, not tags.  
Storage with WORM/retention (e.g., S3 Object Lock) if you need hard immutability.  
Don’t confuse Artifact (the file) with Maven’s artifactId (the name part of those coordinates).  
What does a “webapp.war” contain?  
A WAR (Web Application Archive) is just a ZIP file with a standard layout for Java web apps (Servlet/JSP/Jakarta EE). Typical structure:  
webapp.war  
├── index.html / JSPs / static files (css, js, images, etc.)  
├── META-INF/  
│ └── MANIFEST.MF  
└── WEB-INF/  
├── web.xml (deployment descriptor; optional in modern apps)  
├── classes/ (compiled .class files in package folders)  
├── lib/ (third-party .jar dependencies)  
├── tags/ or *.tld (JSP tag libraries, if used)  
└── application configs (e.g., Spring XML/YAML, faces-config.xml, etc.)  
In short:  
/WEB-INF/classes → your compiled code  
/WEB-INF/lib → all the libraries your app needs  
/WEB-INF/web.xml → how the app maps servlets/filters/listeners (often replaced by annotations nowadays)  
Root files (HTML/JSP/CSS/JS/images) → what the server can serve directly  
How it’s used  
You deploy the WAR to a servlet container (Tomcat, Jetty, WildFly/JBoss). The container reads WEB-INF metadata, loads the classes and libs, and serves the app at a context path (e.g., /webapp). (Contrast: many modern Spring Boot apps ship as a runnable “fat JAR” with embedded Tomcat, instead of a WAR.)  
How to look inside a WAR  
Because it’s a ZIP:  
Linux/macOS: jar tf webapp.war or unzip -l webapp.war  
Extract: jar xvf webapp.war or unzip webapp.war  
Windows: open with 7-Zip/WinZip  
Bonus: how a WAR gets built  
With Maven, the maven-war-plugin packages your compiled classes + resources + dependencies into that structure when you run mvn package.
