### Key components

| Component | What it does | Simple analogy |
|---|---|---|
| Client browser | Sends HTTP/HTTPS requests and displays responses | Customer placing an order |
| Apache Tomcat | Receives HTTP requests and runs Java web applications | Restaurant premises and service staff |
| Java web application (WAR) | Runs application logic, including authentication | Chef preparing the order |
| JDBC | Java API for interacting with relational databases | Standard way to request information |
| JDBC driver | Implements database-specific communication | Interpreter for a particular database |
| JNDI | Allows an app to look up a named resource | Directory for finding a service |
| DataSource | Provides database connections to an app | Connection provider |
| Connection pool | Reuses database connections | Shared, reusable equipment |
| Database | Stores and retrieves application data | Organized storage room |

**Important:** Tomcat does not automatically query the database for every request. The **Java application** decides when and how to access it.

## 2. Step-by-step: Student login example

Imagine a student opens the NIT Academy student portal:

```text
http://192.168.1.98:8080/student/login
```

This IP address and path are **lab examples**, not a claim about a currently deployed portal.

### Step 1 — Browser sends an HTTP request

After the student enters their username and password, the browser submits a request, for example:

```http
POST /student/login HTTP/1.1
Host: 192.168.1.98:8080
Content-Type: application/x-www-form-urlencoded

username=student1&password=example
```

- The browser communicates with Tomcat over **HTTP or HTTPS**.
- The browser **does not use JDBC** to access the database.
- Use **HTTPS**, rather than HTTP, for real logins so credentials are encrypted in transit.

### Step 2 — Tomcat receives the request

Tomcat listens on a configured HTTP port (often **8080** by default) and routes the request to the deployed Java application.

An example deployment location on Linux:

```text
/opt/tomcat/webapps/student.war
```

**WAR** = *Web Application Archive*. It packages a Java web application for deployment.

### Step 3 — Java application processes the login

The application's code determines what needs to happen: find the account, verify the supplied password, apply authorization rules, and generate a response.

A database query might be:

```sql
SELECT student_id, password_hash
FROM students
WHERE username = ?;
```

The `?` indicates a **parameterized query**, which is safer than concatenating user input into SQL. Passwords should be verified against a **secure stored hash**, not compared against plaintext passwords.

### Step 4 — The application uses JDBC

**JDBC** stands for **Java Database Connectivity**. It is a Java API, **not** another server or network protocol used by the browser.

Example Java code (illustrative; requires a configured `dataSource`):

```java
String sql = "SELECT student_id, password_hash FROM students WHERE username = ?";

try (Connection conn = dataSource.getConnection();
     PreparedStatement stmt = conn.prepareStatement(sql)) {

    stmt.setString(1, "student1");

    try (ResultSet rs = stmt.executeQuery()) {
        if (rs.next()) {
            // The application can use the returned account record.
            // Password verification occurs in application code.
        }
    }
}
```

The JDBC driver handles communication with the specific database product.

### Step 5 — The application borrows a pooled connection

Instead of opening a new physical database connection for every operation, a pooled `DataSource` can provide an existing connection.

1. App calls `dataSource.getConnection()`.
2. Pool gives the app an available connection, or creates one if permitted and needed.
3. App executes SQL.
4. App calls `close()` (automatically via Java *try-with-resources* above).
5. For a pooled connection, closing the logical handle normally **returns it to the pool** for reuse.

### Step 6 — Database executes SQL

The database receives the statement, reads the appropriate records, and returns results using its database-specific protocol.

### Step 7 — Application interprets results

The app securely verifies the password, determines whether authentication succeeds, and finishes its business logic.

### Step 8 — Tomcat sends an HTTP response

For example, a successful API response might be:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"status":"success","message":"Login successful"}
```

The browser displays the result. **The database does not directly send HTTP responses to the browser.**

## 3. Why is JDBC mentioned with Tomcat?

There are two main reasons:

1. **Java web application data access.** Applications deployed inside Tomcat use JDBC to read and update data stored in a relational database.
2. **Tomcat-managed connection pooling.** Tomcat can configure a named JDBC `DataSource` and maintain reusable connections for Java applications.

Some applications use a framework-managed connection pool instead of a Tomcat-managed pool. JDBC still provides the underlying Java database API.

## 4. Connection pooling explained

### Without pooling

```text
Request 1 -> OPEN connection -> SQL -> CLOSE physical connection
Request 2 -> OPEN connection -> SQL -> CLOSE physical connection
Request 3 -> OPEN connection -> SQL -> CLOSE physical connection
```

Repeatedly creating database connections introduces network, authentication, and server-resource overhead.

### With pooling

```text
                 +--------------------------------------+
Request 1 ------>|                                      |
Request 2 ------>|  Pool: [Conn 1] [Conn 2] [Conn 3]    |<---> Database
Request 3 ------>|                                      |
                 +--------------------------------------+
                      Borrow -> Query -> Return
```

A pool reduces connection setup work and controls concurrent database connections.

**Example:** If 20 requests simultaneously need a database connection but the pool allows only 5 active connections, at most 5 can use connections at that instant. Other requests wait for a connection to become available or eventually time out. Actual behavior depends on pool configuration, application request patterns, and connection duration.

**Clarification:** A pool can create connections **on demand**. It does not always open every configured connection ahead of time.

## 5. JDBC vs. JNDI vs. DataSource vs. Connection Pool

| Term | Full name / meaning | Role |
|---|---|---|
| JDBC | Java Database Connectivity | Java API for SQL/database operations |
| JDBC driver | Database-specific driver | Connects JDBC operations to a specific database |
| JNDI | Java Naming and Directory Interface | Finds a configured resource by its name |
| DataSource | `javax.sql.DataSource` | Supplies JDBC connections |
| Connection pool | Reusable connection manager | Manages and reuses database connections |

**Remember:** JNDI does not execute SQL; JDBC does not replace Tomcat; and connection pooling does not replace the database.

## 6. Example: Configure a Tomcat JDBC DataSource

A common per-application configuration location is:

```text
/opt/tomcat/conf/context.xml
```

For a single app, configuration may alternatively reside in its own context configuration. The exact layout depends on how Tomcat is deployed.

Example using Tomcat's JDBC pool:

```xml
<Context>
  <Resource
      name="jdbc/StudentDB"
      auth="Container"
      type="javax.sql.DataSource"
      factory="org.apache.tomcat.jdbc.pool.DataSourceFactory"
      driverClassName="org.postgresql.Driver"
      url="jdbc:postgresql://dbserver:5432/studentdb"
      username="studentapp"
      password="REPLACE_WITH_SECRET"
      initialSize="2"
      maxActive="20"
      maxIdle="10"
      maxWait="10000" />
</Context>
```

**Important configuration distinction:** The example above explicitly selects **Tomcat JDBC Pool**, which uses `maxActive` and `maxWait`. Tomcat's default **DBCP 2** pool uses different property names such as `maxTotal` and `maxWaitMillis`. Do **not** mix property names from the two pooling implementations.

| Parameter | Meaning |
|---|---|
| `name` | JNDI resource name |
| `type` | Java interface supplied to the application |
| `factory` | Pooling implementation |
| `driverClassName` | PostgreSQL JDBC driver |
| `url` | Database protocol, host, port, and database name |
| `initialSize` | Connections created when pool initializes |
| `maxActive` | Maximum active pool connections |
| `maxIdle` | Maximum idle connections retained |
| `maxWait` | Maximum wait (milliseconds) for a connection |

Additional requirements:

- Install the **matching PostgreSQL JDBC driver JAR** where Tomcat can load it (typically `$CATALINA_BASE/lib`, or `$CATALINA_HOME/lib` for a simple single-instance setup).
- Make sure the database host, port, credentials, and permissions are valid.
- Avoid committing passwords to Git or distributing real secrets in training material.
- Limit database access to appropriate hosts and ports using firewall rules.

### Application performs the JNDI lookup

```java
import javax.naming.Context;
import javax.naming.InitialContext;
import javax.sql.DataSource;

Context ctx = new InitialContext();
DataSource dataSource = (DataSource) ctx.lookup("java:comp/env/jdbc/StudentDB");
```

The app now calls `dataSource.getConnection()` when it needs a connection.

## 7. Common ports in the lab

| Service | Common port | Network use |
|---|---:|---|
| Apache HTTP Server | TCP 80 / 443 | HTTP / HTTPS |
| Apache Tomcat | TCP 8080 | HTTP (frequently used default) |
| MySQL / MariaDB | TCP 3306 | Database protocol |
| PostgreSQL | TCP 5432 | Database protocol |
| Oracle database listener | TCP 1521 | Oracle Net |

**Note:** These are common defaults. The same IP address cannot have two different processes independently bind to the same TCP port simultaneously. Use distinct ports or IP addresses, or use a reverse proxy for HTTP applications.

Linux command to inspect listening services:

```bash
sudo ss -tulpn
```

Filter for common application/database ports:

```bash
sudo ss -tulpn | grep -E ':(80|443|8080|3306|5432)\b'
```
