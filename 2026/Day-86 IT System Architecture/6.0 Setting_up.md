# Lesson 5 — Cloning, Setting Up, and Building the Minisys Application

**Course:** NIT Academy — Implementing Software Architecture of a Large-Scale IT System  
**Topic:** Connecting to the Google Cloud VM, cloning Bitbucket source code, installing dependencies, initializing PostgreSQL, and building the application.

> **Teaching note:** This lesson follows the supplied lecture. Some script names and database identifiers were unclear in the transcript; students must verify the actual names in the repository before executing them. Commands labeled *illustrative* are examples, not verified commands from the project.

## Learning objectives

By the end of this lesson, students should be able to:

1. Connect to an Ubuntu Compute Engine VM using browser-based SSH.
2. Clone the Minisys source repository over HTTPS.
3. Locate and inspect project installation scripts.
4. Install build-time and runtime dependencies using the repository's scripts.
5. Initialize PostgreSQL and inspect databases, tables, and seed data.
6. Run the project's build script, review output, and prepare for a VM backup.

## 1. Prerequisites

- A running Google Compute Engine Ubuntu VM (the lecture calls it **Workstation 1**).
- Permission to connect using **SSH** in the Google Cloud console.
- Network access for downloading source code and software dependencies.
- The course Bitbucket repository: <https://bitbucket.org/newtechways/minisys-nxt/src/master/>.
- Adequate disk space, RAM, and time for a first build.

**Important:** The original project and scripts may have been written for an older Ubuntu release and older Java/Node/Python versions. Inspect their contents and compatibility before running on Ubuntu 24.04 LTS. Do not assume that an older installation script is safe or compatible with a newer OS.

## 2. Connect to Workstation 1

1. Sign in to <https://console.cloud.google.com/>.
2. Select the project containing the VM.
3. Navigate to **Compute Engine → VM instances**.
4. Find **Workstation 1** and confirm its status is **Running**.
5. Click **SSH** to open a terminal session in the browser.

Verify the system:

```bash
whoami
hostname
pwd
cat /etc/os-release
free -h
nproc
lsblk
```

**Concept:** SSH provides an encrypted remote shell. The VM's external IP can be used for other SSH methods, but browser SSH avoids needing to configure a separate local client for this exercise.

## 3. Clone the codebase from Bitbucket

The lecture uses the **HTTPS** clone option rather than SSH because the latter requires an appropriately configured SSH key and repository access.

```bash
# Verify Git is installed
git --version

# Install Git if it is missing
sudo apt update
sudo apt install -y git

# Clone the project
git clone https://bitbucket.org/newtechways/minisys-nxt.git

# Inspect the downloaded files
cd minisys-nxt
pwd
ls -la
```

If cloning fails, confirm the repository is accessible and that the URL and any required credentials are correct. Do not paste passwords or access tokens into class screenshots.

### Understanding `git clone`

| Command | Purpose |
|---|---|
| `git --version` | Check the Git installation |
| `git clone URL` | Download a working copy of a Git repository |
| `cd minisys-nxt` | Enter the project directory |
| `ls -la` | Display files, including hidden files |
| `git status` | Inspect the working tree |
| `git remote -v` | View configured remote repositories |

## 4. Locate and review installation scripts

The instructor describes two scripts in a scripts directory:

- **Install build tools:** Dependencies required to compile/build the source code.
- **Install test/runtime tools:** Dependencies required to execute and test the application, including PostgreSQL.

The transcript's exact script filenames are not reliable. **Find the real filenames rather than guessing.**

```bash
cd ~/minisys-nxt
find . -maxdepth 4 -type f \( -name '*.sh' -o -name '*.bash' \) | sort
find . -maxdepth 4 -type f -iname '*install*' | sort
```

For each relevant script:

```bash
# Replace PATH_TO_SCRIPT with the actual path found above
sed -n '1,200p' PATH_TO_SCRIPT
bash -n PATH_TO_SCRIPT
```

Review package repositories, downloads, `sudo` operations, database changes, and compatibility requirements before running a script. Only run scripts from sources you trust.

### Software mentioned in the course

| Software | Role |
|---|---|
| Python 3 | Runs the Django web application and supporting scripts |
| Node.js / npm | Builds or serves the React single-page application |
| OpenJDK | Runs Java/Spring Boot services |
| Maven | Builds Java components and resolves dependencies |
| PostgreSQL | Stores application data |
| Git | Retrieves and tracks source code |

The course reference originally specified **OpenJDK 11**. Confirm the project's actual Java version requirement before selecting a JDK; newer releases are not automatically compatible with older builds.

## 5. Run the project's setup scripts

The lecture runs the **build-tools installer first**, followed by the **runtime/test-tools installer**. Substitute the verified script paths from your clone.

```bash
# Illustrative syntax only — use the actual repository filenames
bash PATH_TO_BUILD_TOOLS_INSTALLER
bash PATH_TO_RUNTIME_TOOLS_INSTALLER
```

The installation can take several minutes. Read any errors before proceeding.

Verify installed tools:

```bash
python3 --version
node --version
npm --version
java -version
mvn -version
psql --version
```

Some tools might not be installed globally or may require a new shell session. If a command is missing, inspect the installer output rather than assuming it succeeded.

## 6. Confirm PostgreSQL is running

The lecture explains that the runtime setup creates and starts PostgreSQL as a service.

```bash
sudo systemctl status postgresql --no-pager
```

If the service is installed but stopped:

```bash
sudo systemctl start postgresql
sudo systemctl status postgresql --no-pager
```

**Security:** Keep PostgreSQL private to the VM unless remote access is genuinely needed. The default database port is `5432`; do not open it to the entire internet.

## 7. Create the application database schema

The instructor runs a **schema creation script** supplied with the repository. It creates the application database, tables, indexes, and initial records. The transcript's database name and schema-script filename are unclear, so inspect the actual project scripts and configuration first.

```bash
cd ~/minisys-nxt
find . -maxdepth 5 -type f \( -iname '*schema*' -o -iname '*database*' -o -iname '*dataset*' \) | sort
```

After identifying and reviewing the script, execute it using the instructions in the repository. Avoid running schema initialization repeatedly against a database containing valuable data; it may recreate or overwrite tables.

### Inspect PostgreSQL with `psql`

```bash
# Open the PostgreSQL shell as its service account
sudo -u postgres psql
```

Inside `psql`:

```sql
\l                -- List databases
\c DATABASE_NAME  -- Connect to the actual project database
\dt               -- List tables
\d TABLE_NAME     -- Describe a table
SELECT COUNT(*) FROM TABLE_NAME;
\q                -- Exit psql
```

Replace `DATABASE_NAME` and `TABLE_NAME` with names returned by the database. The lecture notes that most initial tables are empty but a **user-authentication table** contains a seeded administrator record. Verify this only in your authorized lab database; do not expose passwords or password hashes in student screenshots.

## 8. Build the complete application

The instructor returns to the repository's root directory and executes a **build-system shell script**. The exact script name is unclear in the transcript.

```bash
cd ~/minisys-nxt
find . -maxdepth 3 -type f -iname '*build*' | sort
```

Inspect the appropriate build script before executing it:

```bash
sed -n '1,220p' PATH_TO_BUILD_SCRIPT
bash -n PATH_TO_BUILD_SCRIPT

# Run only after review
bash PATH_TO_BUILD_SCRIPT
```

The first build may take **around 15 minutes or longer**, depending on network speed and dependency downloads. Maven, npm, and Python package managers may cache dependencies, so later builds can be faster.

### Verify build success

- Check for a final **BUILD SUCCESS** message where applicable.
- Check the shell exit status immediately after the build: `echo $?` (`0` normally means success).
- Inspect build logs for skipped tests, warnings, and dependency errors.
- Locate generated artifacts according to each component's build system.

**Correction to the lecture:** Automated scripts do **not** guarantee a successful build. Operating-system updates, repository changes, dependency availability, and configuration differences can all cause failures.

## 10. Prepare for the next lesson: Back up the VM

The lecture deliberately stops **after the successful build and before running the application**. The next step is to take a backup so students can recover the prepared environment if later experiments fail.

Recommended classroom checkpoint:

1. Confirm the source repository was cloned successfully.
2. Confirm all required runtimes and build tools are installed.
3. Confirm PostgreSQL and the application schema exist.
4. Confirm the application build completes successfully.
5. Take a **Compute Engine disk snapshot or machine image**, following the next lesson's instructions.
6. Record the VM name, region/zone, Ubuntu version, and backup identifier.

**Important:** A disk snapshot does not necessarily capture a transactionally consistent live database. For a database with important data, use an appropriate PostgreSQL backup and a consistent snapshot procedure.

## 11. Troubleshooting reference

| Symptom | Likely cause | First check |
|---|---|---|
| Browser SSH fails | VM stopped, permissions, or SSH configuration | VM status and IAM permissions |
| `git: command not found` | Git not installed | `sudo apt install git` |
| Clone returns 401/403 | Private repository or missing credentials | Repository access and HTTPS URL |
| Installer fails | Unsupported OS or outdated package names | Script contents and `cat /etc/os-release` |
| `java` or `mvn` missing | Installation incomplete or PATH issue | Version commands and installer logs |
| PostgreSQL connection fails | Service stopped or wrong database/user | `systemctl status postgresql` |
| Schema script fails | Missing prerequisites or existing schema | Error output and DB configuration |
| Build fails | Dependency, network, or version mismatch | Build log and tool versions |
| Disk fills during build | Small boot disk or package caches | `df -h` and `du -sh` |
