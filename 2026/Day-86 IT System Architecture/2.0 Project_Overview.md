# Project Overview — Implementing a Large-Scale IT System

**NIT Academy | IT Systems Architecture | Lesson 2**

## Learning objectives

By the end of this lesson, students should be able to:

- Describe the project from source-code download to cloud deployment.
- Explain why a Linux virtual machine is used as a development workstation.
- Identify the roles of Docker, gateway and discovery services, load balancing, observability, caching, messaging, distributed databases, and Kubernetes.
- Describe the iterative process used to evolve a simple system into a distributed architecture.

The course includes a downloadable source-code repository hosted on **Bitbucket**. Students will download the code and build and run an end-to-end application. **The transcript does not provide a repository URL**; obtain it from the course materials.

## 5. Evolve the architecture step by step

### Stage A — Split the application into services

Separate application responsibilities into **specialized services**, preparing them for possible evolution into microservices.

### Stage B — Routing and service discovery

As the system becomes distributed, add:

- **Netflix Zuul** as an API gateway for routing requests.
- **Netflix Eureka** as a service-discovery component.
- **Load balancing**, including the lecture's **Netflix Ribbon** for client-side load balancing, alongside server-side load-balancing concepts.

> **Technology context:** Zuul and Ribbon are part of the course's original Netflix OSS architecture. For a new production design, evaluate currently maintained gateway and load-balancing alternatives rather than assuming these older components are the best default.

### Stage C — Scale application services

Increase the number of instances of selected services to distribute requests and accommodate higher traffic. Scaling introduces additional operational needs, especially for routing, monitoring, and data consistency.

### Stage D — Add observability

| Capability | Tools in the lecture | Purpose |
|---|---|---|
| Centralized logging | Elasticsearch, Fluentd, Kibana | Collect, store, search, and visualize logs |
| Distributed tracing | Jaeger | Follow requests across multiple services |
| Metrics | Prometheus | Collect and query operational measurements |

*Transcript clarification:* The spoken transcript contains several garbled product names. This lesson uses **Fluentd, Kibana, Jaeger, and Prometheus** based on the described functions and accompanying architecture context; check the original course assets if exact tooling matters.

### Stage E — Handle larger data workloads

- **Redis caching:** reduce repeated reads and improve response times.
- **RabbitMQ messaging:** support asynchronous processing and decouple producers from consumers.
- **Apache Cassandra:** introduce a distributed database and data partitioning for workloads that benefit from this model.

The transcript refers to replacing an earlier database, but its name is unclear. We therefore call it the **original database** rather than guessing its product.

### Stage F — Deploy and operate with Kubernetes

Once the system contains multiple services and supporting infrastructure, deploy it using **Kubernetes on Google Cloud** (Google Kubernetes Engine, or GKE).

Kubernetes helps manage application deployments, service networking, scaling, and recovery, but it does not automatically solve every application-level architecture challenge.

## 7. The architecture improvement cycle

At every stage of the project, repeat the same process:

1. **Identify the current limitation.** What breaks, slows down, or becomes hard to operate?
2. **Evaluate options.** Which architectural patterns and tools could address the problem?
3. **Select a component or approach.** Explain the trade-offs.
4. **Make code and configuration changes.** Integrate the new component.
5. **Build and run the complete system.** Verify the application still works.
6. **Observe the results.** Check behavior, logs, traces, metrics, and performance as appropriate.
7. **Repeat.** Use the next limitation to guide the next improvement.

## 10. Knowledge check

1. Why does the course start with a Linux VM on Google Compute Engine?
2. What problem does Docker packaging help solve?
3. How is a gateway different from a service-discovery server?
4. Why might multiple instances of a service require load balancing?
5. What is the difference between logging, tracing, and metrics?
6. When would caching help? When would asynchronous messaging help?
7. What is the purpose of a distributed database such as Cassandra?
8. Why introduce Kubernetes after the architecture becomes more complex?
9. What steps should be repeated after every architectural change?

## 11. Key takeaways

- Start with a **working end-to-end application**, not a collection of disconnected tools.
- Evolve the system **incrementally**, guided by real architectural limitations.
- Use **Docker** for consistent packaging and **Kubernetes** for orchestrated deployment.
- Introduce **routing, discovery, load balancing, observability, caching, messaging, and distributed storage** as the system's needs grow.
- **Build, run, verify, and observe** the complete system after each change.
