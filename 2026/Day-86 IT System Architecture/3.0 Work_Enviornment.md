# Creating a Work Environment

**NIT Academy | IT Systems Architecture | Lesson 3**  
**Project:** Minisys — Building an End-to-End Application  
**Format:** Student lesson and hands-on lab

> **Source note:** The original lecture and the uploaded *Work Environment Setup* PDF describe a Google Cloud Ubuntu VM with **4 vCPUs and 16 GB RAM**, the **Minisys** Bitbucket codebase, and a specific application stack. The setup commands and operational safeguards below are **additional teaching guidance**, not commands copied from the source. So, verify compatibility before installing newer software versions.

## 1. Learning objectives

By the end of this lesson, students should be able to:

1. Explain why a cloud VM can serve as a development workstation.
2. Create and connect to an Ubuntu VM on Google Compute Engine.
3. Clone a project repository using Git and inspect its contents.
4. Identify the required runtimes and build tools.
5. Describe the Minisys application architecture and its service ports.
6. Validate the environment and recognize common setup problems.

## 2. What are we building?

We will rent a Linux virtual machine on **Google Cloud Compute Engine**, clone the **Minisys** codebase from Bitbucket, and prepare the machine to build and run the system. The VM acts as our workstation as we gradually evolve the application into a distributed architecture.

### Original environment specification

| Component | Course specification | Purpose |
|---|---|---|
| Cloud | Google Cloud | Host the virtual machine |
| Service | Compute Engine | Provision and manage the VM |
| Operating system | Ubuntu Linux | Development environment |
| CPU | 4 vCPUs | Application builds and services |
| Memory | 16 GB RAM | Run several components concurrently |
| Repository | `https://bitbucket.org/newtechways/minisys-nxt/src/master/` | Minisys source code |
| Software | Python 3, Node.js, OpenJDK 11, Maven, PostgreSQL | Application development and runtime |

**Sizing note:** You can start smaller, but the complete multi-service application may need more memory. A VM is billable while resources are provisioned; check current Google Cloud prices, disk charges, and your account's free-trial eligibility. **Do not assume a 4-vCPU/16-GB VM is free.**

## 4. Lab A — Create an Ubuntu VM on Google Cloud

### Step 1: Open the console

1. Sign in at <https://console.cloud.google.com/>.
2. Select or create a Google Cloud project.
3. Ensure billing is configured and the **Compute Engine API** is enabled.
4. Open **Compute Engine → VM instances → Create instance**.

### Step 2: Configure the VM

| Setting | Suggested lab selection |
|---|---|
| Name | `nit-minisys-dev` |
| Region / zone | Choose a suitable available location |
| Machine type | A machine offering **4 vCPUs / 16 GB RAM** (for example, `e2-standard-4`, where available) |
| Boot image | Ubuntu LTS, with version chosen for compatibility |
| Boot disk | At least 30–50 GB recommended for lab work; monitor disk usage |
| Network | Default VPC or a controlled lab VPC |
| External access | Prefer SSH-in-browser, IAP, or a restricted source IP |

**Version caution:** The original course specifies **OpenJDK 11**. A newer Ubuntu LTS release may not provide that exact runtime through its default repositories. Select a compatible Ubuntu release or use an appropriate supported JDK distribution. Check the repository's actual requirements before committing to versions.

### Step 3: Configure firewall access securely

- Allow **SSH (22)** only through a controlled access path; avoid exposing it to the whole internet.
- Do **not** expose PostgreSQL port **5432** publicly.
- The application ports in the source diagrams are for the **development architecture**, not a recommendation to open every port to the internet.
- For browser testing, use SSH tunnels or narrowly scoped firewall rules.

### Step 4: Connect to the VM

Use **SSH** in the Compute Engine console or your configured SSH client. Once connected:

```bash
whoami
hostname
cat /etc/os-release
nproc
free -h
lsblk
pwd
```

Expected checks: Ubuntu is running, CPU count is approximately 4, and RAM is approximately 16 GB (some memory is reserved by the OS).

```bash
find . -maxdepth 2 -type f \
  \( -name 'README*' -o -name 'pom.xml' -o -name 'package.json' \
     -o -name 'requirements*.txt' -o -name 'Dockerfile*' \) \
  -print
```

Read project instructions and inspect scripts before executing them:


The PDF shows two entry points: a **React single-page app** and a **Python/Django web app**, backed by four **Java/Spring Boot** services and a **PostgreSQL** database.

### Service inventory and port map (PDF page 5)

| Component | Technology (PDF page 6) | Port in source diagram |
|---|---|---:|
| Single-page application | React / Node.js tooling | `3000` |
| Web application | Python / Django | `8000` |
| User Authentication service | Java / Spring Boot | `8082` |
| Product service | Java / Spring Boot | `8083` |
| Order service | Java / Spring Boot | `8084` |
| Inventory service | Java / Spring Boot | `8085` |
| Database | PostgreSQL | `5432` |

These are **course-diagram ports**, not guaranteed current runtime defaults. Verify actual configuration in the source code.

### Check listening services after startup

```bash
sudo ss -lntp
# Filter for the ports used in the course diagram:
sudo ss -lntp | grep -E ':(3000|8000|8082|8083|8084|8085|5432)\b'
```

For a local HTTP service, test from the VM first:

```bash
curl -I http://127.0.0.1:3000
curl -I http://127.0.0.1:8000
```

A failed connection is normal **until the corresponding component is started**. A `404` or `405` response can still indicate that an HTTP server is running.

## 8. How to access a web service without opening public ports

For a VM reachable by SSH, local port forwarding can expose a **development** service safely to your laptop. Example using a configured SSH host:

```bash
ssh -L 8000:127.0.0.1:8000 USER@VM_ADDRESS
```

Then visit `http://localhost:8000` on your laptop. If using Google Cloud SSH-in-browser or IAP, follow the applicable tunnel method. The application may need to bind to `127.0.0.1` or `0.0.0.0` as appropriate; prefer loopback binding for a single-VM lab.

## 9. Troubleshooting guide

| Problem | Possible cause | First check |
|---|---|---|
| VM cannot be reached | SSH permissions / firewall / VM state | Compute Engine instance status and SSH path |
| `git clone` fails | URL unavailable, private repository, credentials | Open source URL and check access |
| `java: command not found` | JDK not installed | `java -version`; `apt-cache policy` |
| Java build fails | Incompatible JDK or Maven version | `mvn -version`, `pom.xml` |
| Frontend build fails | Node/npm version mismatch | `node -v`, `package.json` |
| PostgreSQL connection refused | Database not running or wrong host/port | `systemctl status postgresql`, `ss -lntp` |
| Port is already used | Another process bound to port | `sudo ss -lntp` |
| Out of memory | Several services running on small VM | `free -h`, `top` |
| Disk full | Builds, logs, packages | `df -h`, `du -sh` |

## 12. Golden rules and key takeaways

- **Start with the original course architecture**, then verify versions against the actual codebase.
- **One VM is the initial workstation**, not the final production architecture.
- **A port number is not permission to expose a service publicly.**
- **Inspect before executing:** read README, dependency manifests, and shell scripts.
- **Validate each layer:** OS → tools → repository → database → application services.
- **Control cloud costs:** stop/delete resources when finished, and monitor attached storage and IP charges.
