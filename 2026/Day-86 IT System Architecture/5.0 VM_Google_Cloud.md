# Lesson 4 — Creating a Virtual Machine on Google Cloud

**Course:** NIT Academy — Implementing Software Architecture of a Large-Scale IT System  
**Topic:** Provision an Ubuntu Linux workstation using Google Compute Engine  
**Level:** Beginner–Intermediate  
**Estimated lab time:** 30–60 minutes

> **Lesson context:** This guide updates the provided course transcript. Google Cloud Console menus, prices, promotions, and machine availability can change. Always check the current values displayed in your own account before creating resources.

## 1. Learning objectives

By the end of this lesson, students should be able to:

1. Sign in to Google Cloud and create or select a project.
2. Enable billing and the Compute Engine API when prompted.
3. Create an Ubuntu Linux VM with approximately **4 vCPUs and 16 GB RAM**.
4. Explain regions, zones, machine types, boot disks, and external IP addresses.
5. Compare a standard VM with a **Spot VM** and understand interruption risks.
6. Connect to the VM using browser-based SSH and verify its configuration.
7. Stop or delete unused resources to control costs.

## 3. Step 1 — Sign in to Google Cloud

1. Open **https://console.cloud.google.com/** in a browser.
2. Sign in using an eligible Google account. A Gmail account can be used.
3. Review any billing or trial prompts.
4. If you are new to Google Cloud, follow the guided setup to create or link a billing account as required.

**Cost note:** The original lecture mentions a **$300 / 90-day** trial. Promotions and eligibility may change; **do not assume any free credits are available**. Check the offer and your billing page directly.

## 4. Step 2 — Create a Google Cloud project

1. At the top of the Console, open the **project selector**.
2. Select **New Project**.
3. Enter a descriptive project name, such as `nit-academy-it-systems-lab`.
4. If your account has no organization, use **No organization** where offered.
5. Select a location/organization only if your account requires it.
6. Click **Create**, wait for provisioning, and select the new project.

**Important:** The **project name** is a display label; the **project ID** must be globally unique and may be generated or edited during creation. Record the project ID.

**Student checkpoint:** Write down your project name and project ID. Do not share billing account details or credentials.

## 5. Step 3 — Open Compute Engine

1. In the Console navigation, locate **Compute Engine → VM instances** (or search for *VM instances*).
2. If prompted, enable the **Compute Engine API** and wait for initialization.
3. Select **Create instance**.

The Compute Engine instance creation page may group settings under sections such as **Machine configuration**, **OS and storage**, **Networking**, and **Advanced**. Labels may differ from older videos.

## 6. Step 4 — Configure the VM

### 6.1 Instance name, region, and zone

- **Name:** `workstation-1`
- **Region:** choose a nearby region where the required machine type is available.
- **Zone:** choose an available zone within that region.

**Region** is a geographic area; a **zone** is a deployment location inside a region. Proximity can affect latency and pricing.

### 6.2 Select CPU and memory

Under machine configuration, choose a machine family and type that provides **4 vCPUs and 16 GB RAM**. An **E2 custom** configuration may be suitable if available.

A smaller VM can be used for early demonstrations, but builds, multiple services, and databases may require resizing later. Before resizing, stop the instance if required and review the new price.

### 6.3 Select Ubuntu

1. Find **Boot disk** or **OS and storage**.
2. Click **Change** or edit the boot disk.
3. Choose **Ubuntu** as the operating system.
4. Select **Ubuntu 24.04 LTS** (or **22.04 LTS** if needed for compatibility).
5. Choose a disk type and size; **30–50 GB** is a more practical starting point for this project than the original 10–12 GB.
6. Save the boot-disk configuration.

**Why not Ubuntu 21.04?** The lecture's Ubuntu 21.04 reference is obsolete and that release is end-of-life. Supported LTS releases are preferable for new student labs.

**Ubuntu Pro** is optional and may have different licensing/support costs. It is not required for this basic lesson.

### 6.4 Networking and access

- Keep the VM in an appropriate VPC/subnet.
- Use browser-based **SSH** or another approved SSH access method.
- Avoid opening ports `3000`, `8000`, `8082–8085`, or `5432` to the entire internet just to complete VM creation.
- If you later need web access, use narrowly scoped firewall rules, authenticated proxies, or secure tunnels.
- An external IP is useful for direct access but may incur charges and is not always necessary for browser SSH.

## 7. Step 5 — Understand standard VMs versus Spot VMs

The original video demonstrates a **preemptible** VM to reduce cost. Google Cloud now commonly presents **Spot VMs** as the preferred interruptible option.

| Feature | Standard VM | Spot VM |
|---|---|---|
| Relative compute price | Regular | Discounted, varies |
| Can be interrupted by Google Cloud | Not for ordinary capacity reclamation | **Yes, at any time** |
| Suitable for | Reliable lab sessions, persistent development | Restartable builds, experiments, disposable workloads |
| Availability | Subject to capacity and quota | Subject to spare capacity |
| Best student use | Initial setup and guided exercises | Optional cost-optimization lab |

**Important correction:** A Spot VM interruption is **not** a guarantee that the same VM will automatically restart immediately. Behavior depends on the configured termination action, restart policy, capacity, and instance configuration. **Persistent disks generally preserve their data if retained**, but **local SSD and unsaved in-memory work can be lost**, and deleting a VM may delete its boot disk depending on disk auto-delete settings.

**Recommendation:** Begin with a **standard VM** to complete the installation lab. Consider Spot only after students understand interruptions and have saved code to Git and data to persistent storage.

## 8. Step 6 — Review pricing and create

Before clicking **Create**:

1. Review the **estimated monthly/hourly cost** in the Console.
2. Confirm whether the estimate includes compute, disks, network traffic, and external IP charges.
3. Confirm the selected **provisioning model** (standard or Spot).
4. Review firewall and network access settings.
5. Confirm project and region.
6. Click **Create**.

The source lecture quotes **$123/month** for a standard VM and **$41/month** for an interruptible VM. **These are historical examples, not current quotes.** Pricing depends on region, machine type, usage, disks, discounts, and other charges. Use the live estimate and the [Google Cloud Pricing Calculator](https://cloud.google.com/products/calculator).

## 9. Step 7 — Confirm the instance is running

Return to **Compute Engine → VM instances** and confirm:

- Instance name: `workstation-1`
- Status: **Running**
- Machine configuration: approximately **4 vCPUs / 16 GB RAM**
- Boot disk: Ubuntu LTS
- Zone and region are correct
- External IP (if one was assigned)

**Note:** An external IP may change after stop/start unless it is reserved as a static IP; static external addresses may also incur charges.

## 10. Step 8 — Connect using SSH

1. In the **VM instances** table, find `workstation-1`.
2. Click **SSH** if available and permitted.
3. Allow the browser SSH window to open.
4. Run the following commands:

```bash
whoami
hostname
pwd
cat /etc/os-release
uname -r
nproc
free -h
lsblk
ip -br addr
df -h
```

**What these commands verify**

| Command | Purpose |
|---|---|
| `whoami` | Logged-in username |
| `hostname` | VM hostname |
| `pwd` | Current directory |
| `cat /etc/os-release` | Ubuntu version |
| `uname -r` | Linux kernel version |
| `nproc` | Available processing units |
| `free -h` | RAM |
| `lsblk` | Block devices and disks |
| `ip -br addr` | Network interface addresses |
| `df -h` | Mounted filesystem capacity |

> **Do not paste private SSH keys, API tokens, or billing credentials into screenshots or assignments.**

## 12. Step 10 — Save money and clean up

When finished:

- **Stop** the VM if you want to resume later. Stopping usually stops CPU/RAM runtime charges, **but persistent disks, reserved addresses, and other resources may continue to cost money**.
- **Delete** the VM if no longer needed, after backing up code and checking which disks will be deleted.
- Set up a **Cloud Billing budget and alerts** for the lab project. Alerts notify you; they do **not** automatically cap charges.
- Avoid leaving an unused VM running overnight.
- Keep source code in Git rather than only on the VM.

## 13. Common mistakes and troubleshooting

| Symptom | Likely cause | Suggested action |
|---|---|---|
| Cannot create VM | Billing/API not enabled, quota or permissions issue | Check billing, API status, IAM, and quotas |
| Desired machine type missing | Region/zone limitation or quota | Select another zone or suitable machine type |
| SSH fails | IAM, OS Login, firewall, browser policy, or VM startup issue | Check instance status, SSH access configuration, and serial logs |
| VM stops unexpectedly | Spot interruption or maintenance/configuration | Inspect instance events and provisioning model |
| Disk full during build | Boot disk too small | Increase disk capacity and expand filesystem as needed |
| Unexpected charges | Running VM, disk, external IP, or network usage | Review Billing reports and resource inventory |
| Older course commands fail | Ubuntu/Java/Node/tool versions changed | Inspect repo requirements and use supported versions |

## 16. Key takeaways

- **Compute Engine** provisions virtual machines on Google Cloud.
