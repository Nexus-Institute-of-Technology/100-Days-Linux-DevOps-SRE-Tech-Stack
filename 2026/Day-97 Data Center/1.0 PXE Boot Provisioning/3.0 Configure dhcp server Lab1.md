# NIT Academy — Kickstart Lab 01: Configure DHCP for PXE Boot

**Course:** Linux System Administration — Automated Installation with Kickstart  
**Platform:** RHEL 8 / Rocky Linux 8 (BIOS-based PXE demonstration)  
**Lab:** 01 of the Kickstart Server series  
**Objective:** Prepare local YUM/DNF repositories, install the DHCP service, and configure DHCP to provide IP addresses and PXE boot information to new client machines.

> **Lab scope:** This lab configures **DHCP only**. The TFTP service, PXE boot files, OS repository hosting, and Kickstart file are configured in subsequent labs.

## 1. Lab architecture

For this training lab, one Linux server will eventually perform three roles:

1. **DHCP:** Assign an IP address and tell the target machine where to find its boot file.
2. **TFTP/PXE:** Transfer the initial network bootloader and related boot files.
3. **Installation server:** Serve installation media/packages (often HTTP; NFS or FTP may also be used).

The client may be a VMware vCenter VM, a VM on another hypervisor, or a bare-metal system. Configure its firmware/network adapter to **boot from the network (PXE)**.

```text
                   Administrator / vCenter
                            |
                     Power on client
                            v
                     +--------------+
                     | PXE Client VM|
                     |  (no OS yet) |
                     +--------------+
                       |          ^
           DHCP Discover|          |DHCP Offer / ACK + PXE options
                       v          |
              +-------------------------+
              | Kickstart Lab Server    |
              | 192.168.209.139/24      |
              | DHCP service (Lab 01)   |
              | TFTP service (Lab 02)   |
              | OS repository (later)   |
              +-------------------------+
```

## 2. Lab IP addressing and assumptions

| Item | Lab value |
|---|---|
| Kickstart/DHCP/TFTP server | `192.168.209.139` |
| Example subnet | `192.168.209.0/24` |
| Subnet mask | `255.255.255.0` |
| DHCP client pool | `192.168.209.140`–`192.168.209.150` |
| PXE next-server | `192.168.209.139` |
| BIOS PXE boot filename | `pxelinux.0` |
| Example domain | `lab.example.test` |
| Example broadcast address | `192.168.209.255` |

**Before proceeding:** Confirm your subnet, interface name, gateway, and available IP range. Do **not** activate this DHCP server on a network that already has a DHCP service without isolating the lab or coordinating with its administrator. Multiple DHCP servers on the same broadcast domain can disrupt connectivity. The sample values above come from the lecture and may differ from your network.

> The example uses **legacy BIOS PXE** and `pxelinux.0`. UEFI systems usually require a different bootloader, such as `BOOTX64.EFI` or `grubx64.efi`, and firmware-appropriate DHCP options. We will address that distinction in the PXE/TFTP lab.

## 3. Prerequisites

- One RHEL 8-compatible VM or physical server with root/sudo access.
- RHEL 8 installation ISO attached to the lab server.
- A static server IP and an isolated lab network/virtual switch.
- Client VM(s) connected to the same PXE-enabled lab network.
- A working terminal or console session.

Commands below use `sudo`. If signed in as root, `sudo` can be omitted.

## 4. Step 1 — Inspect network settings

Identify the Linux interface, the IP address, and its NetworkManager connection:

```bash
ip -br address
ip route
nmcli -f NAME,DEVICE,TYPE connection show --active
```

Expected server IP for this example: `192.168.209.139/24`.

To inspect the relevant connection:

```bash
nmcli connection show "<connection-name>" | grep -E 'ipv4.method|ipv4.addresses|ipv4.gateway'
```

The server should have `ipv4.method: manual`, not DHCP.

### Optional: Set the lab server IP statically with NetworkManager

**Only run this if you need to configure the lab interface and have console access.** Replacing a remote connection's IP settings may disconnect your session. Adapt the connection name and gateway to your network.

```bash
sudo nmcli connection modify "<connection-name>" \
  ipv4.method manual \
  ipv4.addresses 192.168.209.139/24

# If your lab has a gateway, configure the correct address separately:
# sudo nmcli connection modify "<connection-name>" ipv4.gateway <gateway-ip>

sudo nmcli connection up "<connection-name>"
ip -br address
```

For an **isolated PXE-only network**, a gateway is not required if all PXE services and clients are on the same subnet.

## 5. Step 2 — Mount the installation ISO

Discover the optical device:

```bash
lsblk -f
```

Mount the attached ISO to `/mnt` (this assumes `/dev/sr0` is your virtual CD-ROM):

```bash
sudo mkdir -p /mnt
sudo mount /dev/sr0 /mnt
ls /mnt
```

You should find directories named `BaseOS` and `AppStream` on a complete RHEL 8 installation ISO.

> If the ISO is already mounted at `/mnt`, do not mount it again. If your device is not `/dev/sr0`, substitute the correct device shown by `lsblk`.

## 6. Step 3 — Configure local YUM/DNF repositories

RHEL 8 uses **DNF** as the package manager; `yum` is available as a compatible command. A local ISO-based repository allows package installation without relying on external repositories.

Create the repository configuration file:

```bash
sudo tee /etc/yum.repos.d/local-media.repo >/dev/null <<'EOF_REPO'
[BaseOS]
name=RHEL 8 Local BaseOS
baseurl=file:///mnt/BaseOS
enabled=1
gpgcheck=0

[AppStream]
name=RHEL 8 Local AppStream
baseurl=file:///mnt/AppStream
enabled=1
gpgcheck=0
EOF_REPO
```

**Security note:** `gpgcheck=0` is a lab-only simplification for trusted, locally attached media. For production, validate repository signatures and use configured GPG keys.

Refresh metadata and verify the repositories:

```bash
sudo dnf clean all
sudo dnf repolist
```

Expected output includes `BaseOS` and `AppStream`. If you need to use **only** the local repositories for a package installation:

```bash
sudo dnf --disablerepo='*' --enablerepo=BaseOS --enablerepo=AppStream repolist
```

Do not remove other repository files unnecessarily; temporary `--disablerepo` options are safer.

## 7. Step 4 — Install the DHCP service

Install the ISC DHCP server package:

```bash
sudo dnf install -y dhcp-server
```

Check that it is installed:

```bash
rpm -q dhcp-server
```

The service is called **`dhcpd`** and its primary configuration file is:

```text
/etc/dhcp/dhcpd.conf
```

### Packages mentioned in the lecture

The lecture also mentions `xinetd`, `tftp`, `tftp-server`, and `syslinux`. These are **not required to configure DHCP in Lab 01**. Availability of `xinetd` varies by distribution/repository, and modern RHEL-family TFTP setups often use `systemd` socket activation instead. Install and configure the appropriate PXE/TFTP components in **Lab 02**.

## 8. Step 5 — Back up and configure DHCP

Back up the existing file before editing:

```bash
sudo cp -a /etc/dhcp/dhcpd.conf /etc/dhcp/dhcpd.conf.bak
```

Edit it using your preferred editor:

```bash
sudo vi /etc/dhcp/dhcpd.conf
```

Use the following example, adjusting settings for your actual lab network:

```conf
# NIT Academy — Kickstart Lab 01 (BIOS PXE)
authoritative;
allow booting;
allow bootp;

default-lease-time 600;
max-lease-time 7200;

option domain-name "lab.example.test";

subnet 192.168.209.0 netmask 255.255.255.0 {
    range 192.168.209.140 192.168.209.150;
    option subnet-mask 255.255.255.0;
    option broadcast-address 192.168.209.255;

    # Set the correct gateway only if your lab has one:
    # option routers 192.168.209.1;

    # TFTP server address — same host as DHCP in our lab
    next-server 192.168.209.139;

    # Legacy BIOS PXE bootloader, supplied in Lab 02
    filename "pxelinux.0";
}
```

### What the DHCP configuration means

| Directive | Purpose |
|---|---|
| `authoritative;` | Declares this DHCP server authoritative for its configured network; use only on an isolated/authorized subnet. |
| `allow booting;` | Permits BOOTP/PXE-style network boot support. |
| `allow bootp;` | Permits BOOTP clients. |
| `default-lease-time 600;` | Sets the default address lease duration to 600 seconds. |
| `max-lease-time 7200;` | Sets the maximum lease duration to 7200 seconds. |
| `subnet ... netmask ...` | Defines the subnet served by DHCP. |
| `range ...` | Defines the IP pool assigned to client devices. |
| `option subnet-mask` | Provides subnet mask information. |
| `option broadcast-address` | Provides the subnet broadcast address. |
| `option routers` | Supplies a default gateway when one exists. |
| `next-server 192.168.209.139;` | Tells PXE clients which server to contact for initial boot files. |
| `filename "pxelinux.0";` | Specifies the bootloader filename for **legacy BIOS PXE** clients. |

**Important:** The DHCP server does **not** transfer the bootloader. It supplies the **TFTP server location** and **filename**. In Lab 02, TFTP must actually serve `pxelinux.0` from its configured TFTP root.

## 9. Step 6 — Validate the DHCP configuration

Check syntax before starting the service:

```bash
sudo dhcpd -t -cf /etc/dhcp/dhcpd.conf
```

If the command reports no syntax errors, proceed.

## 10. Step 7 — Start and enable DHCP

```bash
sudo systemctl enable --now dhcpd
sudo systemctl status dhcpd --no-pager
```

Expected service state:

```text
Active: active (running)
```

Verify that DHCP is listening on UDP port **67**:

```bash
sudo ss -lunp | grep ':67'
```

If `firewalld` is active, permit DHCP traffic **on the trusted lab network**:

```bash
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --zone=<lab-zone> --add-service=dhcp --permanent
sudo firewall-cmd --reload
```

Replace `<lab-zone>` with the zone assigned to your **isolated lab interface**. Avoid opening DHCP on an untrusted/public network.

## 11. Step 8 — Confirm DHCP client assignments

Start a test client on the same isolated network. Its NIC must be configured to obtain an IP automatically. You can test an existing Linux client before setting up PXE boot.

On the DHCP server, inspect assigned leases and logs:

```bash
sudo cat /var/lib/dhcpd/dhcpd.leases
sudo journalctl -u dhcpd -n 50 --no-pager
```

The client should receive an address from:

```text
192.168.209.140 – 192.168.209.150
```

A BIOS PXE client should also receive boot information pointing to:

```text
TFTP server: 192.168.209.139
Boot filename: pxelinux.0
```

A client may still fail at the **file download stage** because TFTP has not yet been configured. That is expected at the end of Lab 01.

## 12. Troubleshooting

| Symptom | Check | Suggested action |
|---|---|---|
| `dhcpd` will not start | `sudo journalctl -xeu dhcpd` | Look for syntax errors, missing subnet declarations, or no matching interface. |
| DHCP configuration syntax error | `sudo dhcpd -t -cf /etc/dhcp/dhcpd.conf` | Correct the reported directive or missing semicolon. |
| Client receives no IP | `ip -br address`, `sudo ss -lunp \| grep ':67'` | Confirm the server and client are on the same isolated L2 network and DHCP is running. |
| Client receives wrong subnet | Other DHCP services on same network | Isolate the virtual switch/network and eliminate competing lab DHCP servers. |
| Client receives IP but PXE download fails | `next-server`, `filename` | DHCP may be correct; TFTP and boot files are configured in Lab 02. |
| `dnf` cannot find the local packages | `ls /mnt/BaseOS /mnt/AppStream` | Confirm the **complete** installation ISO is mounted and repo paths are correct. |
| `dhcpd` complains about interfaces | `ip -br address` | Ensure the configured subnet matches an address assigned to the server's lab NIC. |
