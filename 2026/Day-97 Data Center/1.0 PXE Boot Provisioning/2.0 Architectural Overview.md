# Kickstart Server Architecture — Lecture Notes

**Topic:** Automated Linux installation using Kickstart and PXE  
**Level:** Linux System Administration / RHCSA preparation

## 1. Introduction

In this lecture, we will discuss the **architecture of a Kickstart installation environment** and understand how a client machine installs Linux automatically over the network.

A typical network-based Kickstart installation uses:

1. **DHCP service** — gives the client network settings and, when configured, PXE boot information.
2. **TFTP service** — supplies initial network-boot files in a traditional PXE setup.
3. **Installation repository server** — provides operating system installation files and packages over **HTTP, HTTPS, FTP, or NFS**, depending on the Linux distribution and installer support.
4. **Kickstart configuration file (`ks.cfg`)** — supplies the installation instructions to the Anaconda installer.

> **Lab design:** For learning purposes, DHCP, TFTP, the Kickstart file, and the OS repository can all be hosted on **one Linux server**. In a production environment, these services are separated.

## 2. Main Components

| Component | Purpose | Information or files provided |
|---|---|---|
| Administration console | Creates and powers on a virtual machine or manages a physical server | VM settings and network-boot selection |
| Target node / client | Machine receiving Linux | Requests network and installation resources |
| DHCP server | Assigns network settings and may direct PXE clients to a boot server | IP address, gateway, boot-server information, boot filename |
| TFTP server | Serves initial boot files for traditional PXE | `pxelinux.0`, configuration files, `vmlinuz`, `initrd.img` |
| Kickstart file server | Hosts the automated installation answer file | `ks.cfg`, commonly via HTTP/HTTPS |
| Installation repository | Supplies Linux installation content | Installer source and RPM packages |

## 3. Step-by-Step Installation Workflow

### Step 1 — Power on the target machine

The administrator logs in to a management console, such as **VMware vCenter**, and creates or selects a new VM. 
- Instead of booting from a DVD or ISO, 
- the VM is configured to **boot from the network**.

The same idea works with a bare-metal server whose firmware supports network boot.

### Step 2 — Client requests an IP address

When network boot starts, the client uses DHCP to discover network settings. The client must first obtain sufficient networking information to communicate with the boot service.

### Step 3 — DHCP supplies network and boot information

The DHCP infrastructure responds with information such as:

- Client IP address and subnet mask
- Default gateway and, optionally, DNS server
- PXE boot-server address
- Network boot filename, such as `pxelinux.0` in a legacy BIOS PXE deployment

The exact information and delivery method depend on the DHCP/PXE configuration.

### Step 4 — Client retrieves the initial bootloader

For a **legacy BIOS PXE** installation, the client downloads `pxelinux.0` from the **TFTP server**.

**PXE** stands for **Preboot Execution Environment**. It allows compatible systems to start a boot process over the network without inserting a local USB drive or DVD.

**TFTP** stands for **Trivial File Transfer Protocol**. TFTP is a lightweight file-transfer protocol, generally without authentication or encryption, so it should be used only on appropriately controlled networks.

### Step 5 — Client retrieves the boot configuration, kernel, and initramfs

The PXE bootloader reads its configuration and loads the installer components:

- **PXE configuration/menu** — identifies boot options and locations of the other files
- **`vmlinuz`** — the Linux kernel
- **`initrd.img`** — the installer initial RAM disk (initramfs)

The boot configuration can also specify where the installer can find the Kickstart file using a boot argument such as:

```text
inst.ks=http://192.168.1.10/ks.cfg
```

*This address is only an example; substitute the real IP address of your lab server.*

### Step 6 — Anaconda reads the Kickstart file

After the installer starts, **Anaconda** retrieves `ks.cfg` from the specified location. The file can define:

- Language, keyboard, and time zone
- Disk partitioning and filesystem choices
- Network settings
- Authentication and users
- Package selection
- Installation source
- `%post` commands to run after installation

The Kickstart configuration reduces or eliminates the need to answer installation prompts manually.

### Step 7 — Installer accesses the OS repository

The installation source is defined in the Kickstart file or through another installer boot option. Anaconda accesses the repository server to retrieve the operating system packages and installation content.

Commonly used transports include **HTTP/HTTPS** and **NFS**. FTP may also be supported in relevant environments.

Example Kickstart installation source:

```kickstart
url --url="http://192.168.1.10/rhel9/"
```

The actual repository path must contain a valid installation tree for the selected distribution.

### Step 8 — Installation completes

Anaconda partitions the disks, installs the selected packages, configures the system, and performs any defined post-installation tasks. The target machine can then reboot into the installed Linux operating system.

## 5. Legacy BIOS PXE vs. UEFI Network Boot

The `pxelinux.0` workflow in this lecture is a **legacy BIOS** example. Newer systems often boot in **UEFI mode** and may use an **EFI bootloader** (such as GRUB EFI or shim) instead of `pxelinux.0`. Some deployments also use HTTP Boot or iPXE rather than relying exclusively on TFTP.

The core Kickstart concept remains the same: boot the installer, provide `ks.cfg`, and make a valid OS installation source available.

## 6. Why This Architecture Is Useful

- **Unattended installation:** Reduces repeated manual input.
- **Consistency:** Uses the same installation instructions across machines.
- **Scalability:** Helps deploy many physical or virtual servers.
- **No local installation media needed:** Network boot avoids creating a separate USB/DVD installer for every target.
- **Post-installation automation:** Scripts and commands can prepare the system for use.

## 8. Lecture Summary

A network-based Kickstart installation is a coordinated process:

**DHCP provides networking → PXE/TFTP supplies boot components → Anaconda reads `ks.cfg` → the OS repository provides installation packages → Linux installs automatically.**
